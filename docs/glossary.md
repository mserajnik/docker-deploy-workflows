# Glossary

This glossary defines each term docker-deploy-workflows uses, some with
examples from a caller repository.

## Terms

| Term              | Meaning                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Caller repository | A repository that calls docker-deploy-workflows to build and publish its images, such as [mserajnik/tortoise-deploy][tortoise-deploy].                                                                                                                                                                                                                                         |
| Upstream          | A project outside the caller repository that it builds from or follows. Every source is an upstream. So is each repository under `drift.upstreams`, which only drift checks read, such as [MariaDB/mariadb-docker][mariadb-docker], whose entrypoint the database image of mserajnik/tortoise-deploy extends.                                                                  |
| Source            | An upstream Git repository that an image builds from. [mserajnik/cmangos-deploy][cmangos-deploy] has three: `core` (`cmangos/mangos-{variant}`), `db` (`cmangos/{variant}-db`), and `playerbots`. `sources` declares each source once, and its `repository` and `branch` may contain `{variant}`.                                                                              |
| Primary source    | The source with the actual software, which `primary-source` names. Its commit is set as `org.opencontainers.image.revision`. In mserajnik/cmangos-deploy that is `core`, and in [mserajnik/lost-city-rs-deploy][lost-city-rs-deploy] `engine`.                                                                                                                                 |
| Variant           | One build of the software, and the main build axis. mserajnik/tortoise-deploy has `base`, `modules`, and `modules-bots`. mserajnik/cmangos-deploy has one variant per expansion, and [mserajnik/vmangos-deploy][vmangos-deploy] and mserajnik/lost-city-rs-deploy have one per client or game version. A variant lists the sources it builds from, or builds from all of them. |
| Image             | An entry of `images`, with its Dockerfile and its package, such as mserajnik/tortoise-deploy's `server` image in the `tortoise-server` package. `images` is an ordered list.                                                                                                                                                                                                   |
| Image slot        | The position of an image in `images`, which is also the build order. An image builds only when no earlier image failed. mserajnik/tortoise-deploy, for example, lists its server image first, so a failed server build also holds back its database image. There are at most three slots.                                                                                      |
| Share group       | Variants that publish one image between them, as `share` on the image declares. The image builds once, from the first variant's commits, and gets every member's tags. mserajnik/tortoise-deploy's database image uses `share: {base: [modules]}`, and mserajnik/vmangos-deploy's uses one group of all eight client versions.                                                 |
| Leg               | The build of one image for one share group, or for one variant outside any group. A leg builds on both architectures and then publishes one multi-platform index.                                                                                                                                                                                                              |
| Tag               | A name the registry publishes an image under, such as the template `"{variant}-{commit:core}"`. The up-to-date check reads a leg's last tag.                                                                                                                                                                                                                                   |
| Moving tag        | A fixed tag a variant adds to every image it publishes, such as `latest` on mserajnik/tortoise-deploy's `base`.                                                                                                                                                                                                                                                                |
| Up-to-date check  | The test for whether a leg needs a build. The image behind the leg's last tag has a label per source with the commit it came from. When every label matches the source's current commit, the leg is up to date. A missing package or tag counts as out of date.                                                                                                                |
| Forced rebuild    | A run that builds every leg. A dispatch with `force-rebuild` is one, and so is a scheduled run on a day that `rebuild-day` selects, Monday by default.                                                                                                                                                                                                                         |
| Test run          | A dispatch with `test-run`. It appends `-test` to every package name and skips the badges and retention, so retention never deletes `-test` packages.                                                                                                                                                                                                                          |
| Retention         | The deletion of package versions older than `retention`, at the end of a run whose other jobs completed successfully, except test runs and pull request runs. Tagged versions count too.                                                                                                                                                                                       |
| Badge             | A status badge that `badges` declares. The plan renders each into a badge file, a JSON file in the [shields.io endpoint format][shields-endpoint], and the badge job uploads them over FTP when anything built and retention completed successfully.                                                                                                                           |
| Pin               | The commit a drift check compares against. `pin` sets it on an entry of `sources` or `drift.upstreams`, and `pins` sets it per variant.                                                                                                                                                                                                                                        |
| Drift check       | A comparison of upstream files at the pin and at the current commit. A check can compare files (`files`), require a path not to exist (`absent`), or compare a directory's files (`trees`). Any difference fails the run before anything builds, and the log suggests a new pin.                                                                                               |
| Migration         | An upstream database file that a deployment applies once, on the first start after it appears, such as `sql/database_updates/world/*.sql` in the `core` source of mserajnik/tortoise-deploy. A watch rule matches them with `migrations`.                                                                                                                                      |
| Base file         | An upstream database file that the database image imports only when it creates the database, such as `sql/base/tw_world_*.sql` in the `core` source of mserajnik/tortoise-deploy. A watch rule matches them with `base`.                                                                                                                                                       |
| Migration edit    | An upstream commit that changes a migration an existing database has already applied, or adds or changes a base file, so the database cannot pick the change up by itself. See the [migration edits documentation](migration-edits.md).                                                                                                                                        |
| Target            | A database that migration edits apply to, such as `world` or `characters`. The wire value names each target.                                                                                                                                                                                                                                                                   |
| Remedy            | How a database image is to handle an edit to a target. With `recreate`, it re-creates the database, and with `manual`, the operator applies the change by hand. The wire value does not carry the remedy: the remedy decides which edits the value lists, and the image has to know each target's remedy itself.                                                               |
| Watch rule        | The globs that assign files of a source to a target. A file that `migrations` matches counts when it is changed, moved, or deleted. A file that `base` matches counts in those cases and when upstream adds it. `exclude` removes files from both, and some rule must watch or exclude every file that `claim` matches, or the run fails.                                      |
| Cutoff            | The commit a source's migration-edit scan starts after, set with `cutoff`, or with `cutoffs` per variant. Moving it forward drops the older edits from new images.                                                                                                                                                                                                             |
| Wire value        | The text form of a variant's migration edits, which a database image gets as a build argument, such as `world:core@1a2b...\|characters:`.                                                                                                                                                                                                                                      |
| Var               | A named value under `vars`, which a variant may override, used in templates as `{var:<name>}`. mserajnik/tortoise-deploy's variants use vars for their module lists.                                                                                                                                                                                                           |
